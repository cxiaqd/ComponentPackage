# 面试官问为什么选择webpack而不用vite，该怎么回答呢?
这个问题考察的是你对前端构建工具的理解，以及在实际项目中做技术选型时的权衡能力。你的项目基于 **Vue 2.7 + Vue CLI 4.5**，底层使用 Webpack，可以从以下几个方面组织回答：

---

### 一、项目启动时的时代背景与技术生态

我们项目启动是在 **2020 年左右**，当时 Vite 刚刚发布 1.0 版本，生态还不够完善，尤其是对 Vue 2 的支持尚不稳定，而 Webpack 已经是业界最成熟、生态最丰富的构建工具。Vue CLI 默认底层也是 Webpack，使用它能获得官方最佳实践和强大的插件生态，降低了初期的技术选型风险。

---

### 二、Webpack 的成熟度与项目需求匹配度高

1. **微前端支持**：项目中使用了 `hel-micro` 实现模块联邦，Webpack 5 内置了 Module Federation 能力，虽然当时我们用的是 Webpack 4，但社区已经有很多成熟的插件（如 `webpack-module-federation-plugin`）来支持微前端场景，而 Vite 当时对模块联邦的支持还不够完善。

2. **复杂的代码分割策略**：我们的打包配置中用到了 `LimitChunkCountPlugin` 强制限制 chunk 数量，并针对 `@hui-pro`、`hi-map-vue` 等内部组件库进行了精确的分离和预编译。Webpack 提供了非常细粒度的 splitChunks 配置，能够满足这类复杂的分包需求。

3. **兼容性要求**：项目需要支持较老版本的浏览器（如 IE 11 不在目标列表中，但部分客户环境可能仍使用较低版本的 Chrome）。Webpack 配合 `@babel/preset-env` 可以精确控制 polyfill 的注入，而 Vite 在开发环境下利用原生 ESM，虽然生产构建仍用 Rollup，但在 legacy 浏览器兼容性方面当时没有 Webpack 成熟。

4. **插件生态丰富**：我们需要图片压缩（`compression-webpack-plugin`）、静态资源路径重写、环境变量注入等一系列功能，Webpack 社区有海量插件可以直接组合使用，而 Vite 插件生态当时还在起步阶段。

---

### 三、团队熟悉度与迁移成本

团队所有成员对 Webpack 的配置、调试都非常熟悉，而 Vite 虽然是更快的开发服务器，但它基于原生 ESM 的机制与 Webpack 完全不同，迁移意味着需要重构所有构建配置、处理不同插件之间的兼容性、重新调试热更新逻辑。考虑到项目已经进入稳定迭代期，迁移成本远大于收益。

---

### 四、如果现在重新选型会怎样？

如果现在启动一个全新项目，尤其是基于 Vue 3 的项目，我会优先考虑 **Vite**。因为它带来了极快的开发服务器启动速度、开箱即用的 HMR，以及基于 Rollup 的生产打包性能。但在当时的技术环境和项目约束下，选择 Webpack 是更稳健、务实的选择。

---

### 总结

选择 Webpack 并不是因为它“最好”，而是因为它 **在当时最合适**：生态成熟、配置灵活、与项目需求高度匹配，且团队经验丰富。现在项目依然稳定运行在 Webpack 上，我们也没有盲目追求新工具，而是通过构建优化（代码分割、Gzip、Tree Shaking）持续提升性能，这正体现了我们在技术选型上的务实和工程化思维。
