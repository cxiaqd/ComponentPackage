# 中高级前端工程师面试题及详细答案

## 一、Vue框架相关

### 1. Vue 2.x 的响应式原理是什么？Vue 3.x 有什么改进？

**答案：**

**Vue 2.x 响应式原理：**
- **核心机制**：使用 `Object.defineProperty()` 对对象的每个属性进行劫持
- **实现方式**：
  ```javascript
  function defineReactive(obj, key, val) {
    const dep = new Dep()
    Object.defineProperty(obj, key, {
      enumerable: true,
      configurable: true,
      get() {
        // 依赖收集
        if (Dep.target) {
          dep.depend()
        }
        return val
      },
      set(newVal) {
        if (val === newVal) return
        val = newVal
        // 派发更新
        dep.notify()
      }
    })
  }
  ```
- **局限性**：
  - 无法检测对象属性的添加/删除
  - 无法检测数组索引和长度的变化
  - 必须遍历对象的所有属性，性能开销较大

**Vue 3.x 改进：**
- **使用 Proxy**：解决了 Vue 2.x 的所有局限性
  ```javascript
  const reactive = (obj) => {
    return new Proxy(obj, {
      get(target, key) {
        track(target, key)
        return target[key]
      },
      set(target, key, value) {
        target[key] = value
        trigger(target, key)
      }
    })
  }
  ```
- **性能提升**：Proxy 的性能优于 Object.defineProperty
- **内存占用**：减少了响应式系统的内存占用

### 2. Vue 的生命周期有哪些？在实际项目中如何应用？

**答案：**

**生命周期钩子：**
- **创建阶段**：`beforeCreate` → `created`
- **挂载阶段**：`beforeMount` → `mounted`
- **更新阶段**：`beforeUpdate` → `updated`
- **销毁阶段**：`beforeDestroy` → `destroyed`
- **keep-alive**：`activated` → `deactivated`

**项目中的应用场景：**

```javascript
export default {
  // 1. created: 初始化数据、调用接口
  created() {
    this.initUserInfo()
    this.fetchSearchConfig()
  },
  
  // 2. mounted: DOM操作、第三方库初始化
  mounted() {
    this.initMap()
    this.bindEventListeners()
    this.changeWidth()
  },
  
  // 3. beforeDestroy: 清理工作
  beforeDestroy() {
    this.clearTimer()
    this.removeEventListeners()
  },
  
  // 4. activated: keep-alive缓存组件激活时
  activated() {
    this.refreshData()
  },
  
  // 5. deactivated: keep-alive缓存组件停用时
  deactivated() {
    this.pauseVideo()
  }
}
```

**实际项目中的最佳实践：**
- **created**：数据初始化、接口调用（不涉及DOM）
- **mounted**：DOM操作、第三方库初始化、事件绑定
- **beforeDestroy**：定时器清理、事件解绑、内存泄漏预防
- **activated/deactivated**：缓存组件的数据刷新和暂停

### 3. Vue 组件通信有哪些方式？项目中如何选择？

**答案：**

**通信方式及选择策略：**

| 方式 | 适用场景 | 项目中的应用 |
|------|----------|--------------|
| **props/emit** | 父子组件通信 | 搜索条件传递、结果展示 |
| **$refs** | 父组件调用子组件方法 | 播放器控制、弹窗操作 |
| **$parent/$children** | 简单的父子访问 | 不推荐使用，维护性差 |
| **provide/inject** | 跨层级组件通信 | 主题配置、全局配置 |
| **Vuex** | 跨组件状态共享 | 用户信息、搜索配置 |
| **EventBus** | 简单的跨组件通信 | 项目中使用 Vue.prototype.bus |
| **$attrs/$listeners** | 多层组件透传 | 封装组件时使用 |

**项目中的实际应用：**

```javascript

  @search="handleSearch"
  @reset="handleReset"

    theme: this.theme,

  }

// 4. Vuex - 状态管理

  ...mapGetters({
    currentTargetImgs: 'fusion/getImgs'
  })

// 5. EventBus - 事件总线

// 组件中

this.bus.$on('fullLoading', this.handleLoading)
```

### 4. Vue 的 computed 和 watch 有什么区别？

**答案：**

**区别对比：**

| 特性 | computed | watch |
|------|----------|-------|
| **用途** | 计算属性，派生数据 | 监听数据变化，执行副作用 |
| **缓存** | 有缓存，依赖不变不重新计算 | 无缓存，每次变化都执行 |
| **返回值** | 必须返回值 | 不需要返回值 |
| **异步** | 不支持异步 | 支持异步 |
| **参数** | 无 | 可接收新值和旧值 |

**项目中的应用：**

```javascript
// 1. computed - 计算属性（有缓存，适合计算）
computed: {
  // 简单计算
  filteredList() {
    return this.list.filter(item => item.active)
  },
  
  // 复杂计算
  searchParams() {
    return {
      ...this.baseParams,
      startTime: this.timeRange[0],
      endTime: this.timeRange[1],
      keyword: this.keyword
    }
  },
  
  // Vuex getter
  ...mapGetters({
    currentTargetImgs: 'fusion/getImgs'
  })
}

// 2. watch - 监听器（无缓存，适合副作用）
watch: {
  // 简单监听
  keyword(newVal) {
    this.debounceSearch()
  },
  
  // 深度监听对象
  searchConfig: {
    handler(newVal) {
      this.saveConfig(newVal)
    },
    deep: true,
    immediate: true
  },
  
  // 监听路由变化
  '$route'(to, from) {
    this.initPage(to)
  },
  
  // 异步操作
  playInfo(val) {
    if (val && val.length) {
      this.initPlayer()
    }
  }
}
```

**选择原则：**
- **computed**：需要计算结果、有缓存需求、不涉及副作用
- **watch**：需要执行异步操作、需要副作用、不需要返回值

### 6. Vuex 持久化如何实现？

**答案：**

**项目中使用的持久化方案：**

```javascript
// 1. 简单的 localStorage 持久化（项目中的实现）
export default {
  mutations: {
    // 添加图片上传历史
    addImage(state, img) {
      if (localStorage.getItem('IMAGE_HISTORY')) {
        state.imageHistory = JSON.parse(localStorage.getItem('IMAGE_HISTORY'))
      } else {
        state.imageHistory = []
      }
      
      if (img) {
        // 去重
        state.imageHistory.forEach((Img, i) => {
          if (Img.url === img.url) {
            state.imageHistory.splice(i, 1)
          }
        })
        state.imageHistory.push(img)
      }
      
      // 限制数量
      if (state.imageHistory.length > 5) {
        state.imageHistory.splice(0, 1)
      }
      
      localStorage.setItem('IMAGE_HISTORY', JSON.stringify(state.imageHistory))
    }
  }
}

// 2. 使用 vuex-persistedstate 插件
import createPersistedState from 'vuex-persistedstate'

export default new Vuex.Store({
  plugins: [
    createPersistedState({
      key: 'bsearch-vuex',
      paths: ['userInfo', 'searchConfig', 'imageHistory']
    })
  ]
})

// 3. 自定义持久化插件
const persistPlugin = store => {
  // 初始化时从localStorage恢复
  const savedState = localStorage.getItem('vuex-state')
  if (savedState) {
    store.replaceState(JSON.parse(savedState))
  }
  
  // 状态变化时保存到localStorage
  store.subscribe((mutation, state) => {
    const stateToSave = {
      userInfo: state.userInfo,
      searchConfig: state.searchConfig
    }
    localStorage.setItem('vuex-state', JSON.stringify(stateToSave))
  })
}

export default new Vuex.Store({
  plugins: [persistPlugin]
})
```

**持久化策略：**
- **选择性持久化**：只持久化必要的状态
- **数据压缩**：对大数据进行压缩
- **加密存储**：敏感数据加密存储
- **过期机制**：设置数据过期时间

| **缓存** | contenthash | 利用浏览器缓存 |
| **压缩混淆** | TerserPlugin | 减少代码体积 |

`contenthash` 是**Webpack 等构建工具中用于文件指纹（hash）生成的一种策略**，它根据**文件内容**生成唯一的哈希值，当文件内容发生变化时，哈希值才会改变。

## 一、三种 Hash 的区别

在 Webpack 中，主要有三种 Hash 策略，容易混淆：

| Hash 类型 | 依据 | 特点 | 适用场景 |
|-----------|------|------|---------|
| **hash** | 整个构建过程 | 任何文件变化都会导致所有文件 hash 改变，缓存利用率低 | 很少使用 |
| **chunkhash** | 每个 chunk 的内容 | 同一 chunk 内的文件共享同一个 hash，一个文件变化会影响同 chunk 的所有文件 | 适用于按入口打包的场景 |
| **contenthash** | 单个文件内容 | 只有文件自身内容变化时 hash 才变，其他文件不受影响 | **最适合静态资源（CSS、图片）和长期缓存** |

### 示例说明

假设你有以下文件结构：
```
src/
  ├── index.js (入口)
  ├── utils.js (工具函数)
  └── style.css (样式)
```

**使用 `hash`**：
- 修改 `style.css` → `index.js`、`utils.js`、`style.css` 的 hash 全部改变 ❌

**使用 `chunkhash`**：
- 修改 `style.css` → 主入口 chunk（`index.js` + `utils.js`）的 hash 不变 ✅
- 但 `style.css` 和 `index.js` 在同一个 chunk 中 → 修改 CSS 仍会导致 JS 的 hash 改变 ❌

**使用 `contenthash`**：
- 修改 `style.css` → 只有 `style.css` 的 hash 改变 ✅
- `index.js` 和 `utils.js` 的 hash 保持不变 ✅

## 三、contenthash 与浏览器缓存

### 缓存策略示例（Nginx 配置）

```nginx
location ~* \.(js|css|png|jpg|jpeg|gif|ico)$ {
    expires 1y;           # 静态资源缓存 1 年
    add_header Cache-Control "public, immutable";
}
```

### 工作原理

1. **首次访问**：浏览器下载 `main.a3f2e8d1.js` 并缓存
2. **代码修改后**：重新构建生成 `main.b4c3d2e1.js`（contenthash 改变）
3. **用户再次访问**：HTML 引用新的文件名，浏览器下载新文件
4. **旧文件**：仍然在缓存中，但不会被请求

这种策略实现了**精准缓存**：只更新真正变化的文件，最大化利用缓存。

## 五、常见问题与解决方案

### 问题 1：CSS 改变导致 JS 的 hash 也改变

**原因**：当使用 `MiniCssExtractPlugin` 时，CSS 文件和 JS 文件属于同一个 chunk。

**解决方案**：使用 `contenthash` 且确保 CSS 独立输出：

```javascript
module.exports = {
  optimization: {
    // 将 runtime 代码提取到单独文件
    runtimeChunk: 'single',
    moduleIds: 'deterministic',  // 使用稳定模块 ID
    splitChunks: {
      cacheGroups: {
        styles: {
          name: 'styles',
          type: 'css/mini-extract',
          chunks: 'all',
          enforce: true,
        }
      }
    }
  }
};
```

### 问题 2：vendor 的 hash 频繁变化

**原因**：即使没有修改第三方库，但业务代码变化可能导致模块 ID 变化，从而影响 vendor。

**解决方案**：
```javascript
module.exports = {
  optimization: {
    moduleIds: 'deterministic',  // Webpack 5 默认值
    // 或使用 'hashed' (Webpack 4)
  }
};
```

### 问题 3：哈希长度

可以使用 `[contenthash:长度]` 控制哈希长度：

```javascript
filename: '[name].[contenthash:8].js'  // 取前 8 位
```

**建议**：
- 生产环境使用 8-20 位，平衡唯一性和文件名长度
- 开发环境可以不用 contenthash（使用 `[name].js`）

|------|---------|------|
| **Webpack** | `[contenthash]` | 基于文件内容生成 |
| **Vite** | 默认使用 | Vite 在生产构建时自动为文件名添加 hash |
| **Rollup** | `[contenthash]` | 配置方式类似 |
| **Parcel** | 自动处理 | Parcel 自动处理，无需配置 |

### Vite 示例

Vite 在构建时自动添加 contenthash，无需手动配置：

```javascript
// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        // 可选配置，Vite 有默认值
        entryFileNames: 'assets/[name].[hash].js',
        chunkFileNames: 'assets/[name].[hash].js',
        assetFileNames: 'assets/[name].[hash].[ext]'
      }
    }
  }
};
```

---

## 七、最佳实践总结

1. **JS 文件使用 `[name].[contenthash].js`**
2. **CSS 文件使用 `[name].[contenthash].css`**
3. **图片等静态资源使用 `[name].[contenthash][ext]`**
4. **设置合理的缓存策略**（1 年 + immutable）
5. **使用 `deterministic` 模块 ID** 避免不必要的 hash 变化
6. **开发环境不使用 contenthash**，提升构建速度

这样配置可以实现**最优的长期缓存策略**，最大化用户缓存命中率，提升应用加载速度。

在 Webpack 中，`DllPlugin` 和 `DllReferencePlugin` 是一对用于**分包优化**的插件，主要目的是**将不常变动的第三方库（如 React、Vue、lodash 等）预先打包成独立的动态链接库**，从而提升构建速度和优化缓存。

## 核心原理

- **DllPlugin**：将指定的第三方库打包成一个单独的 DLL 文件（如 `vendor.dll.js`），并生成一个清单文件（manifest.json），记录模块的映射关系。
- **DllReferencePlugin**：在正常的项目构建中，引用该清单文件，避免重复打包已经打包过的库。

## 配置示例

### 1. 创建 DLL 打包配置文件 `webpack.dll.config.js`

```javascript
const path = require('path');
const webpack = require('webpack');

module.exports = {
  mode: 'production',
  entry: {
    // 指定需要打包的第三方库
    vendor: ['react', 'react-dom', 'lodash']
  },
  output: {
    path: path.resolve(__dirname, 'dist/dll'),
    filename: '[name].dll.js',
    // 暴露全局变量
    library: '[name]_[fullhash]'
  },
  plugins: [
    new webpack.DllPlugin({
      // 生成的清单文件路径
      path: path.join(__dirname, 'dist/dll', '[name]-manifest.json'),
      // 与 output.library 保持一致
      name: '[name]_[fullhash]'
    })
  ]
};
```

### 2. 运行 DLL 打包

```bash
webpack --config webpack.dll.config.js
```

执行后会生成：
- `vendor.dll.js`：包含 React 等库的打包文件
- `vendor-manifest.json`：模块映射清单

### 3. 主项目配置中使用 `DllReferencePlugin`

```javascript
const webpack = require('webpack');
const path = require('path');

module.exports = {
  // ...其他配置
  plugins: [
    new webpack.DllReferencePlugin({
      context: __dirname,
      // 引用清单文件
      manifest: require('./dist/dll/vendor-manifest.json')
    })
  ]
};
```

### 4. 在 HTML 中引入 DLL 文件

需要在 `index.html` 中手动添加 `<script src="dist/dll/vendor.dll.js"></script>`，或通过 `HtmlWebpackPlugin` 自动注入。

## 优势

| 优势 | 说明 |
|------|------|
| **构建速度提升** | 第三方库只需打包一次，后续开发构建时直接引用，无需重复打包 |
| **缓存优化** | DLL 文件独立，第三方库更新频率低，可利用浏览器缓存长期缓存 |
| **代码分割** | 业务代码和第三方库分离，降低主包体积 |

## 注意事项

⚠️ **Webpack 5 的变化**

在 Webpack 5 中，官方推荐使用 **`persistent caching`**（持久化缓存）来替代 `DllPlugin`，因为 Webpack 5 内置的缓存机制已经能提供类似的构建优化效果，且配置更简单。

```javascript
// Webpack 5 配置持久化缓存
module.exports = {
  cache: {
    type: 'filesystem', // 使用文件系统缓存
    buildDependencies: {
      config: [__filename] // 配置文件变化时重新构建
    }
  }
};
```

## 适用场景

- **Webpack 4 及更早版本**：`DllPlugin` 仍是有效的优化手段
- **大型项目**：第三方依赖众多，构建频繁时收益明显
- **CI/CD 环境**：可配合 `DllPlugin` 缓存依赖层，加快部署速度

## 替代方案

- **Webpack 5 持久化缓存**：官方推荐，配置更简单
- **HardSourceWebpackPlugin**（已停止维护）
- **使用 `splitChunks`**：配合 `cacheGroups` 提取公共代码，适用于生产环境

## 总结

`DllPlugin` 是 Webpack 生态中经典的构建优化工具，虽然 Webpack 5 有了更好的内置方案，但在维护旧项目或需要精细控制依赖打包时，理解 `DllPlugin` 的使用仍然很有价值。如果你使用的是 Webpack 5，建议优先考虑持久化缓存方案。

export function handleError(error) {
  if (error.response) {
    const { status, data } = error.response
    
    switch (status) {
      case 401:
        // 未授权
        redirectToLogin()
        break
      case 403:
        // 禁止访问
        showMessage('无权限访问', 'error')
        break
      case 404:
        // 资源不存在
        showMessage('资源不存在', 'error')
        break
      case 500:
        // 服务器错误
        systemError({
          title: data.msg,
          errorCode: data.code,
          traceCode: data.traceCode
        })
        break
    }
  } else if (error.request) {
    // 请求超时
    showMessage('请求超时，请重试', 'error')
  } else {
    // 其他错误
    showMessage('系统错误', 'error')
  }
}
